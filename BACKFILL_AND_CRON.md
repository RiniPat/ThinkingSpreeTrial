# Backfill + cron — operational guide

Two new pieces added in this addendum:

1. **`scripts/src/backfill-sprint-emails.ts`** — one-time backfill of historical pre-sprint emails from Gmail into the new `sprint_emails` table, so existing sprints get a threading anchor.
2. **`artifacts/api-server/src/routes/cron.ts`** — token-protected endpoint for scheduled cohort sync, plus an updated `render.yaml` that wires up a Render Cron Job to call it every 5 minutes.

---

## 1. Backfill — run once, after deploying migration 010

### What it does

For every existing sprint with no `sprint_emails` row, search the relevant consultant's Gmail Sent box for a message addressed to that founder in the 30 days before the sprint date with a subject matching pre-sprint patterns ("pre-sprint", "preparation", "sprint prep", "t-sprint"). If found, insert a `sprint_emails` row with the real Gmail Message-ID — so post-sprint emails for that sprint will thread correctly.

### What it can't do

- Recover the original email **body**. We insert a placeholder HTML comment. The body isn't needed for threading, only for "view this previous email" UI — if you have that, the placeholder will look empty there.
- See emails sent by accounts that aren't connected to Google in your app.
- Match if the subject diverges wildly from the patterns. Add patterns to `SUBJECT_PATTERNS` at the top of the script if your team uses different phrasing.

### How to run

```bash
# 1. Make sure migration 010 has been applied (the sprint_emails table must exist).
# 2. Dry run first — prints what it would do without writing.
pnpm tsx scripts/src/backfill-sprint-emails.ts --dry-run

# 3. If the output looks sane, run for real.
pnpm tsx scripts/src/backfill-sprint-emails.ts

# 4. (Optional) Narrow the window. Default is 365 days.
BACKFILL_DAYS_BACK=180 pnpm tsx scripts/src/backfill-sprint-emails.ts
```

### What you'll see

```
▶ Backfill starting
  Window: last 365 days
  Candidates: 248 sprints with no pre-sprint email recorded

  Consultant: vani@thinkingspree.com (87 sprints)
  Consultant: saumitra@thinkingspree.com (63 sprints)
  ...

────────────────────────────────────────────
  Matched: 196
  Inserted: 196
  Skipped (no consultant / no founder email): 12
  Unmatched candidates: 40
✓ Done
```

Unmatched sprints aren't broken — their post-sprint emails just won't thread to an earlier conversation. New sprints going forward record their Message-ID at send time, so the problem only affects the historical tail.

## 2. Cron — scheduled cohort sync

### What it does

Every 5 minutes (configurable), a Render Cron Job hits `POST /api/cron/sync-cohorts` on your web service. The route:

1. Pulls every cohort with `source_sheet_url` set.
2. For each, calls `syncCohortFromSheet()` using the cohort creator's Google OAuth tokens.
3. Catches errors per-cohort so one bad sheet doesn't abort the batch — failed cohorts get `last_sync_error` populated, visible in the cohort detail UI's red banner.
4. Returns a JSON summary.

### Setup

#### Step 1. Update `render.yaml`

Replace your current `render.yaml` with the one in this patch bundle's root. The diff vs. your current file:

- Adds `INTERNAL_TOKEN` env var to the web service (auto-generated by Render).
- Adds a second service of type `cron` that calls the sync endpoint.

```bash
git diff render.yaml
git add render.yaml
git commit -m "Add cron job for cohort sync"
git push  # Render picks up the blueprint change automatically
```

After deploy, Render will provision the cron job and start running it on schedule.

#### Step 2. Wire up the cron route

In your Express entry (`artifacts/api-server/src/index.ts` or equivalent), register the router:

```ts
import { cronRouter } from "./routes/cron.js";
app.use("/api/cron", cronRouter);
```

Important: register this **before** any session middleware that would 401 unauthenticated requests. Cron uses bearer-token auth, not sessions.

#### Step 3. Attach source sheets to your cohorts

For each cohort you want auto-synced, set `source_sheet_url`. From the UI:

```
Cohorts → Wadhwani Foundation companies → (top-right) ⋯ → Edit → paste sheet URL → Save
```

Or via API:

```bash
curl -X PATCH https://your-app.onrender.com/api/cohorts/1 \
  -H "Content-Type: application/json" \
  --cookie "session=..." \
  -d '{"sourceSheetUrl": "https://docs.google.com/spreadsheets/d/.../edit", "sourceSheetTab": "Companies"}'
```

#### Step 4. Verify

Wait 5 minutes, then check:

- `GET /api/cohorts` should show `lastSyncedAt` is recent.
- The cohort detail page should show the green "Live-synced" banner.
- Render dashboard → your cron service → Logs should show successful curls.

### Alternatives to Render Cron

If you'd rather not use Render's cron service, the endpoint is plain HTTP — any scheduler works:

- **GitHub Actions** (free for public repos, generous for private):
  ```yaml
  # .github/workflows/sync-cohorts.yml
  on:
    schedule: [{ cron: "*/5 * * * *" }]
  jobs:
    sync:
      runs-on: ubuntu-latest
      steps:
        - run: |
            curl -sS -X POST \
              -H "Authorization: Bearer ${{ secrets.INTERNAL_TOKEN }}" \
              "https://your-app.onrender.com/api/cron/sync-cohorts"
  ```

- **cron-job.org** — set up a free job pointing at the URL, add a custom header `Authorization: Bearer <token>`.

- **In-process timer** — for a smaller team, you can also just `setInterval(syncAll, 5 * 60 * 1000)` inside the web service. Risk: if the free Render web service spins down due to inactivity, the timer goes with it. The dedicated cron job avoids that.

### Tuning the schedule

The default `*/5 * * * *` (every 5 minutes) is generous. Each run takes ~1–3 seconds per cohort. For 10 cohorts on the free tier, this is fine. If you want to be gentler on the Google Sheets API:

| Cron expression | Frequency |
|---|---|
| `*/5 * * * *` | every 5 minutes (default) |
| `*/15 * * * *` | every 15 minutes |
| `0 * * * *` | hourly |
| `0 9-21 * * 1-5` | hourly during business hours, weekdays only |

### Manual fallback

Even with cron running, the "Sync now" button on the cohort detail page still works — useful when a consultant just added a row to the sheet and doesn't want to wait 5 minutes.
